# Runbook — эксплуатационные инциденты

Приложение — демонстрационный магазин: товары вымышлены, доставки нет, платежи работают только в локальной симуляции или Stripe test mode. Подготовленная конфигурация не доказывает успешную доставку писем, оповещений или подключение Stripe.

## Быстрая диагностика

- Здоровье: `GET /actuator/health`; диагностика `/actuator/metrics` и `/actuator/prometheus` требует ADMIN. Публичный health не раскрывает подробности.
- Каждый HTTP-ответ несёт `X-Request-Id`; ошибки содержат тот же `requestId` и стабильный `code`. В prod логи используют JSON/ECS.
- Исходные alert rules: [ops/prometheus-rules.yml](../ops/prometheus-rules.yml). Владелец должен подключить scraper и получателя и проверить доставку. Не отключать авторизацию метрик ради scraper.
- Доступные функции: `GET /api/v1/storefront/config`. `UNAVAILABLE` означает, что требуемая конфигурация не подключена; настроенный sender не гарантирует доставку.

## Неизвестный результат создания платежа

`PAYMENT_OUTCOME_UNKNOWN` / HTTP 503 означает, что провайдер мог принять запрос. Не создавать новый платёж с новым ключом, не отменять заказ и не снимать резерв вручную. Повтор клиента использует тот же сохранённый idempotency key. Неопределённые Stripe-операции сохраняют резерв до выяснения результата; обычный TTL их не освобождает.

1. Проверить `shopupu.payments{result=create_unknown}`, состояние платежа и историю событий без вывода секретов/полного provider body в логи.
2. Проверить выбранный **тестовый** Stripe account, доступность сети и native webhook `POST /api/v1/payments/stripe/webhook`. Не заменять Stripe-подпись старым callback secret.
3. Автоматическое восстановление отправляет только сохранённое исходное тело с исходным ключом в пределах 23 часов. После этого повторное создание автоматически прекращается.
4. Найти исходную Checkout Session в том же test account по metadata `shopupu_payment_id` и `shopupu_order_id`. ADMIN может вызвать `POST /api/v1/admin/payments/{id}/recover-stripe-session` с `{ "sessionId": "cs_test_..." }`. Сервер читает и проверяет существующую сессию; новая операция у Stripe не создаётся. Для открытой сессии восстанавливается проверенный checkout URL.
5. Если результат всё ещё неизвестен, оставить операцию для расследования. Отсутствие ответа или истечение локального таймера не доказывает отказ Stripe.

Только локальные stub-платежи безопасно истекают по внутреннему таймеру. Переход браузера на success URL не является подтверждением оплаты. Подписанный callback или проверенное восстановление должны пройти привязку к заказу, сумме, валюте и test object; повтор не даёт второй SALE.

## Возврат и расхождение статусов

`REFUND_OUTCOME_UNKNOWN` / HTTP 503 и состояния refund `UNKNOWN`/`PENDING` блокируют новый возврат. Автоматическое восстановление читает существующий refund по ID или исходным metadata. В интерфейсе ADMIN следует дождаться результата. Только подтверждённый `FAILED`/`CANCELED` позволяет явный повтор с предыдущим `refundOperationKey`; повторный клик воспроизводит ту же заменяющую операцию.

Успешный полный демонстрационный возврат переводит платёж и заказ в REFUNDED и возвращает остаток один раз. Ручная смена статуса заказа на PAID/REFUNDED запрещена. Частичные или dashboard refunds без metadata операции не входят в этот сценарий и требуют отдельной сверки; не исправлять связанные таблицы по одной.

Джоба сверки каждые 15 минут читает до 100 подходящих платежей выбранного провайдера с курсором, даёт webhook 5 минут и смотрит последние 24 часа. Она сообщает о расхождении, но не меняет состояние. Метрики: `reconciliation_mismatch`, `reconciliation_lookup_failed`. Одна ошибка провайдера не прерывает весь пакет. Для потерянного webhook запросить повторную доставку оригинального события; для неизвестного create использовать процедуру выше. Старые операции за пределами окна требуют операторской сверки.

Не менять Stripe account/provider, пока остаются неизвестные операции. Подробности настройки и контрольные сценарии: [external-integrations.md](external-integrations.md).

## Почта, AI и рост ошибок

- При `EMAIL_DELIVERY_UNAVAILABLE` проверить явный `NOTIFICATION_PROVIDER`, выбранный sender и конфигурацию. Не говорить пользователю, что письмо отправлено. После восстановления он может запросить новое одноразовое письмо.
- Для подключённой почты проверять `shopupu_notification_delivery_total` по `kind`/`outcome`. Очередь ограничена, запускается после commit и не переживает остановку процесса. Метрика `accepted` означает успешный ответ почтового провайдера, не доставку адресату; успешный HTTP-ответ пользователю не ждёт даже этого этапа. Order email — best effort.
- `AUTH_RATE_LIMITED`, `AI_RATE_LIMITED` и `RATE_LIMITED` возвращают 429 с `Retry-After`. Не повышать лимиты автоматически и не доверять присланному клиентом `X-Forwarded-For`. Сначала проверить источник и профиль нагрузки.
- AI quotas действуют на один процесс и сбрасываются при рестарте; включать провайдера только с внешним spending cap. При деградации интерфейс обозначает подбор по каталогу. [ai-guardrails-2026-09-12.md](ai-guardrails-2026-09-12.md).
- При росте 5xx сопоставлять `requestId`, трассу и бизнес-метрики. Не копировать токены, ссылки сброса и provider credentials в сообщения об инциденте.

## Аккаунт и отзыв сессий

Смена/сброс пароля и повторное использование refresh token увеличивают auth version: старые access/refresh сессии перестают проходить проверку. Обычный logout отзывает цепочку refresh; уже выпущенный access token имеет остаточный срок не более 15 минут. Простое обновление `refresh_tokens.revoked` не отзывает access tokens немедленно и не заменяет штатный сценарий.

ADMIN/MANAGER требуют TOTP, включая вход через Google. Восстановление требует пароль, неиспользованный recovery code и регистрацию нового фактора. Потеря `MFA_ENCRYPTION_KEY` делает сохранённые факторы нечитаемыми; не генерировать замену без процедуры восстановления. Failed-login audit использует хеш нормализованного account identifier; успешный audit коммитится вместе с действием. [identity-remediation-2026-09-12.md](identity-remediation-2026-09-12.md).

## Retention: что удаляется само и когда

`DataRetentionJob` запускается ежедневно в **04:10 UTC** — через полчаса после ночного backup (03:40 UTC), поэтому удалённое ещё 14 дней лежит в снимках, как и обещает страница «Data and privacy». Периоды — `RETENTION_*` в `.env` (по умолчанию: audit-события 12 мес., аккаунты без входа 12 мес., псевдонимизированная история удалённых аккаунтов 24 мес.); менять их без правки страницы нельзя. Что делает job: (1) удаляет `audit_events` старше периода пачками по 500; (2) аккаунты CUSTOMER с `users.last_login_at` старше периода проходят тот же erasure, что GDPR-запрос (`GdprService.anonymizeAccount`), с событием `RETENTION_INACTIVE_ACCOUNT_ERASED`; ADMIN/MANAGER и аккаунты с неизвестным последним входом не трогаются; (3) у аккаунтов с `deleted_at` старше периода удаляются заказы (каскадом платежи, события, доставка, история статусов) и сама строка `users`. `last_login_at` обновляется при каждом входе/регистрации/продлении сессии (не чаще раза в час). Сбой на одном аккаунте логируется как WARN и не останавливает остальные; следующий запуск повторит. Выключить: `RETENTION_ENABLED=false` (страница тогда становится неправдой — только на время инцидента).

## База данных, резервная копия и откат

Проверить health, сетевую доступность, Hikari pool и PostgreSQL connections. Не менять рабочую БД или перезапускать все контейнеры без установленной причины. Production runtime должен использовать отдельную роль без DDL, memberships и владения объектами; миграции выполняет отдельный deployment process.

[database-recovery.md](database-recovery.md) содержит точную процедуру разделения ролей, безопасные backup/restore scripts, проверку восстановленной копии, collation и критерии RPO/RTO. Скрипты требуют явной цели и credentials. Restore drill выполняется только в изолированной пустой БД. Перед открытием трафика после восстановления сверить платёжные операции, которых могло не быть в старой копии.

Откат образа допустим только на конкретный проверенный image digest с совместимой схемой и семантикой. Нельзя утверждать, что все старые образы совместимы: V19 удаляла review title. Новые миграции не редактировать после применения. Восстановление рабочей БД из backup теряет последующие записи и является отдельной операторской процедурой, а не обычным rollback образа.
