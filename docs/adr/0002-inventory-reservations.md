# ADR-0002: Резервирование остатков атомарными UPDATE вместо блокировок

Дата: 2026-07-06 · Статус: принято

## Контекст

Конкурентные чекауты не должны продавать больше, чем есть на складе (INV-03).
Изначальный код делал read-modify-write без блокировок — классический oversell.

## Решение

Отдельная сущность `Inventory (stock, reserved, @Version)` на каждый SKU и
три атомарных перехода одним UPDATE со встроенным условием:

- **reserve**: `SET reserved = reserved + q WHERE stock - reserved >= q`
  — при чекауте; 0 обновлённых строк = OutOfStockException.
- **commitSale**: `SET stock = stock - q, reserved = reserved - q` — при оплате.
- **release**: `SET reserved = reserved - q` — при отмене/истечении TTL.
- **restock**: `SET stock = stock + q` — при возврате.

Каждое движение пишется в журнал `inventory_movements` (INV-06).
Неоплаченные заказы автоматически отменяются по TTL и освобождают резерв.

## Последствия

- (+) Корректность под конкуренцией гарантируется БД (row lock на время UPDATE),
  без пессимистичных блокировок на уровне приложения и без ретраев.
- (+) Подтверждено конкурентным интеграционным тестом (CheckoutConcurrencyIT).
- (−) Доступность = stock − reserved требует join при отображении каталога
  (решено батч-загрузкой availability).

## Альтернативы

`SELECT ... FOR UPDATE` (длиннее держит блокировку, риск дедлоков при
многострочных заказах), оптимистичные ретраи по @Version (сложнее и медленнее
под нагрузкой распродажи).
